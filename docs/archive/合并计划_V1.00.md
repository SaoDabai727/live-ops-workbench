# 合并计划：日报助手（黑蛋助手） × 抖音直播间监控器（巨量百应多直播间工作台）

> 版本：V1.01 ｜ 文档类型：合并方案与架构设计
> 目标产物目录：`G:/AI/直播运营助手`
> 状态：**P0-P6 完成，V1.01 已交付实测**（剩余：累计观看人数正则待 compass 实测确认、P7 Playwright 降级可选）

---

## 0. 执行摘要（结论先行）

两个软件同属**美的系家电抖音直播运营**场景，业务对象完全重合（均为 燃热 / 烟灶 / 小天鹅 三个直播间）：

- **A 日报助手（黑蛋助手 v1.2.0）**：Python + PySide6 桌面端，强项是「单一直播大屏 → 抓取 KPI → 生成可复制日报文本」。
- **B 抖音直播间监控器（巨量百应多直播间工作台 v1.0.24）**：Electron + Node 桌面端，强项是「多直播间监控工作台外壳」（分区分会话、OAuth、视图池/保活、子页导航、私信 WebSocket、自动刷新）。

二者是**天然互补**而非竞争：B 已经为每一个直播间打开了「直播大屏」子页（URL 模板含 `{roomId}`），而 A 正是抓取「直播大屏」生成日报。因此**最优选方案是：以 B 的 Electron 外壳为基座，把 A 的抓取+日报生成逻辑用 JavaScript 改写后嵌入**，形成「统一的多直播间运营工作台 + 每房间一键日报」。

**核心推荐：统一技术栈到 Electron/Node（方案 1）。** 理由：B 的外壳更完整、Electron 使用真实 Chromium（对抖音大屏 UA 兼容性远优于 A 的 QtWebEngine，A 自身已因 WebView 被识别而预留 Playwright 降级方案）；A 的抓取逻辑本质是 JS+正则，迁移成本极低；若反向把 B 的 BrowserView 分区/保活/WebSocket/OAuth 用 Python 重写，工作量与风险都高一个量级。

## 2. 统一技术栈决策（关键分叉）

### 方案 1（推荐）：统一到 Electron/Node，移植 A 逻辑入 B 外壳
- **做法**：以 B 的 Electron 骨架为基础，把 A 的 `translator.py`/`dom_selectors.py` 改写为 JS（`reportGenerator.js`/`reportScraper.js`），嵌入到 B 的「直播大屏」BrowserView 上做一键日报。
- **优点**：外壳最完整；真实 Chromium 对抖音兼容性最好；A 抓取逻辑迁移成本极低（JS+正则）；单一运行时、单一打包链路（electron-builder）；可直接复用 B 已验证的分区/保活/导航。
- **缺点**：放弃 Python 代码；需把 A 的主播/画像/历史等概念并入 B 的房间模型。
- **风险评估**：低。

### 方案 2：统一到 Python/PySide6，移植 B 逻辑入 A
- **做法**：用 pywebview/CEF 在 Python 端重建 BrowserView 分区、保活、OAuth IPC、WebSocket。
- **优点**：保留 A 的抓取代码原样。
- **缺点**：QtWebEngine 已被抖音识别需 Playwright 降级（A 自身待办）；在 Python 中重建分区会话/视图池/WS 工作量是方案 1 的数倍；包体同样 100MB+。
- **风险评估**：高。

### 方案 3：共享外壳 + 双运行时并存
- **做法**：保留两个 EXE，加一个启动器分别唤起，共享配置文件。
- **优点**：几乎不重写。
- **缺点**：两套运行时（Python+Electron）共存、体积翻倍；数据/配置难以真正共享；两窗口割裂体验差。
- **风险评估**：中（架构债高，不推荐）。

> **结论**：采用**方案 1**。下文所有设计均基于方案 1。

## 3. 功能整合方案

1. **保留 B 的多直播间工作台外壳**作为统一主界面（左侧房间栏 + 顶部子页 Tab + 工具栏）。
2. **新增「直播日报」子页（kind=report）**：选中某房间后，该子页不加载 URL，而是由渲染进程面板展示「日报编辑器」（文本框 + 复制 / 保存历史 / 重新抓取 按钮）。
3. **抓取逻辑绑定到「直播大屏」视图**：当用户在「直播大屏」子页时，点击工具栏「生成日报」（或在「直播日报」子页点「重新抓取」），主进程对**当前房间的 daping BrowserView** 执行 `executeJavaScript`（移植自 A 的抓取 JS），得到整页 innerText → `normalizeKpi`（移植自 A 的正则）→ `formatReport` → 通过 IPC 回传渲染进程面板。
4. **主播名单 / 用户画像 / 直播时长**并入房间配置（见 §4），在「直播间管理」弹窗中增加对应编辑项（移植 A 的 `anchor_dialog`）。
5. **历史归档**改为统一 `reports/<roomId>/YYYY-MM-DD.txt`（移植 A 的保存逻辑），并保留对 A 旧 `history/` 的导入。
6. **OAuth / 私信 / 自动刷新 / 保活 / 预加载 / URL 白名单**全部保留，作为统一外壳能力。

## 4. 数据结构统一方案

### 4.1 统一存储根
```
%APPDATA%/LiveOpsWorkbench/            # 不再写死 "美的"，中性命名
├── config/
│   ├── rooms.json        # 统一房间模型（合并 A+B 字段）
│   ├── subPages.json     # 子页定义（新增 report）
│   ├── selectors.json    # 移植 A 的 douyin_dom_selectors（KPI 抓取标签正则）
│   ├── customUrls.json
│   └── navigationState.json
├── web_profile/          # Electron persist: 分区 cookie/localStorage（自动）
├── reports/              # 日报历史
│   └── <roomId>/YYYY-MM-DD.txt
└── logs/debug.log        # 修正 B 的硬编码 D:\ 路径
```

### 4.2 统一房间模型（合并 A 与 B）
```json
{
  "id": "live1",
  "label": "美的燃热",
  "roomId": "123456",
  "anchors": [{"name": "小花", "enabled": true}],   // 来自 A
  "userProfileText": "",                             // 来自 A
  "liveDuration": "15h",                             // 来自 A
  "dailyUrl": ""                                     // 来自 A（兼容；优先用 roomId 模板）
}
```
- B 的 `rooms.json.liveRooms` 提供 `id/label/roomId`；A 的 `rooms` 提供 `anchors/userProfileText/liveDuration/dailyUrl`。

### 4.3 子页定义（subPages.json）新增 report
```json
"report": { "label": "直播日报", "kind": "report", "refreshInterval": 0 }
```
`daping` 子页保持不变（URL 模板含 `{roomId}`，每 60s 自动刷新以保证数据最新）。

### 4.4 selectors.json（移植 A 的 douyin_dom_selectors）
保留 A 的标签正则（如「直播间成交金额」「退款金额」等），作为 KPI 提取规则；用户可在配置中覆盖。

| A（Python） | → 统一产物（Electron/Node） |
|------|------|

**新增统一模块：**
- `main/reportScraper.js`：移植抓取 JS 与 `executeJavaScript` 调用（对指定 BrowserView）。

**构建/打包：** 采用 Electron + electron-builder（B 本就是 Electron 应用，直接复用其打包链路），彻底移除 PyInstaller/Python 依赖。

## 6. 潜在冲突点及解决方案

| # | 冲突点 | 影响 | 解决方案 |
|---|--------|------|----------|
| C1 | 技术栈完全不同（Python/Qt ↔ Electron/Node） | 无法直接共用代码 | 方案 1：以 Electron 为基座，A 逻辑 JS 化移植（见 §2/§5） |
| C2 | 配置目录与 schema 不一致（`BlackEggAssistant` vs `juliang-workbench`，结构不同） | 旧数据丢失/重复 | 统一到 `LiveOpsWorkbench`；写一次性迁移（见 §4.4），按房间 label/name 相似度或索引映射合并 |
| C3 | 房间标识不同（A 用名称作键；B 用 `id`+`label`+`roomId`） | 迁移匹配困难 | 统一房间模型以 `id` 为主键；A 的 3 个房间按 label 匹配 B 的 `liveRooms`，缺失则引导用户补全 `roomId` |
| C4 | 浏览器引擎差异（QWebEngineView vs BrowserView） | A 抓取方式不可用 | 复用 B 的 BrowserView；抓取改为 `view.webContents.executeJavaScript(抓取JS)`，与 A 的 `runJavaScript` 等价 |
| C5 | **B 的 `debugLog.js` 硬编码 `D:\美的抖音直播间项目\logs`** | 换机/非 D 盘必失败；绑定「美的」 | 改为 `app.getPath('userData')/logs/debug.log`，路径可配置，去除业务名硬编码 |
| C6 | 品牌/命名绑定（黑蛋助手、巨量百应、美的） | 通用性、扩展性差 | 统一产品名为「直播运营助手」（用户已指定目录），内部 id 中性化（`live-ops-workbench`） |
| C7 | 抖音大屏 DOM 结构差异（A 选择器基于 class 名，B 的 daping 走 compass.jinritemai.com） | 选择器可能不匹配 | 采用 A 的 **v7 整页 innerText + 标签正则**策略（结构无关），并对 compass 大屏做一轮实测校准 |
| C8 | A 的 OAuth 无、B 的 OAuth 为 MOCK | 抓取需登录态 | 复用 B 的分区 session cookie（登录大屏后自动持有），抓取 JS 在同分区执行即继承登录态，无需单独 OAuth |
| C9 | 主题风格（A 深色 QSS vs B 深海军蓝+青） | 视觉割裂 | 统一为 B 的暗色令牌（navy `#0A0E1A` / 青 `#00E5C0`），A 的 QSS 概念并入 `styles.css` |
| C10 | 日报子页与「直播大屏」视图的引用关系 | 抓取时需定位正确的 BrowserView | 在 `appState.pages[roomId].daping` 维护该房间 daping 视图引用；report 子页触发时回退到该引用执行抓取 |


**数据流（生成日报）：**
1. 用户在侧栏选房间 → 进入「直播大屏」子页（B 已加载 `compass.../live_room_id={roomId}`，分区 cookie 保持登录）。
2. 点「生成日报」或切到「直播日报」子页 → 渲染进程发 IPC `generate-report {roomId}`。
3. 主进程 `reportManager` 对该房间 daping BrowserView 执行 `executeJavaScript(抓取JS)`（移植 A）→ 整页 innerText。
4. `reportGenerator.normalizeKpi(innerText)`（移植 A 正则）→ KPI 字典；结合房间配置（主播/时长/画像）→ `formatReport` → 日报文本。
5. IPC `report-result` 回传渲染进程面板展示；用户可「复制」或「保存历史」（写入 `reports/<roomId>/YYYY-MM-DD.txt`）。
